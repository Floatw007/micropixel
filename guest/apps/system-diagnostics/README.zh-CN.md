# 设备诊断应用

面向开发、装配和现场排障的交互式诊断程序。它把测试分成独立模块，记录通过/失败状态，并用统一日志格式输出关键结果，便于串口采集器定位问题。

## 当前测试项目

| 项目 | 检查内容 | 判定方式 |
| --- | --- | --- |
| 语音输入 | Audio Input 能力、采样格式、PCM 数据是否变化、峰值和动态范围 | 自动；测试时需对着设备说话 |
| 语音输出 | Audio Output 能力、提示音提交和物理扬声器链路 | API 自动检查 + 人工确认是否听到 |
| 大模型 | 语音配置、在线路由、会话启动、用户转写、模型回复文本 | 自动；不要求扬声器播放成功 |
| 完整语音流程 | Listening、转写、模型回复、Speaking/首个音频、会话正常结束、丢帧 | 自动，显示各阶段延迟 |
| Wi-Fi / 网络 | Network 路由、语音网关路由、断开后恢复 | 状态自动读取；Wi-Fi 开关需进入系统设置手动操作 |
| 触摸 / 显示 | 四象限触摸事件和画面区域 | 自动计数，四区均触发后通过 |
| 持久存储 | KV 写入、读取校验、删除 | 自动 |
| 稳定性巡检 | 5 分钟周期检查 Network、Voice 和诊断接口；检测测试期间重启 | 自动；需保持本页运行，重启后再次打开应用会标记上次巡检异常中断 |

日志采用 `diagnostics: test=<name> result=<state> ...` 格式。应用不会输出网络地址、凭据、设备标识或语音配置内容。

## 已知边界

- Guest 没有 Wi-Fi 扫描、开关和凭据管理权限，因此网络页只能读取服务状态并打开 Host 系统设置。自动扫描、自动发现语音网关和重连策略应实现于 Host，而不是应用内。
- “大模型测试”仍借助完整语音服务取得输入转写，但只以回复文本作为成功条件；当前 Voice ABI 没有独立的纯文本 LLM 请求接口。
- 扬声器、屏幕颜色、触摸准确性最终都涉及物理现象，不能仅凭 API 返回值宣称硬件正常。
- 应用内巡检不能替代 Host 串口 panic、watchdog、PSRAM、AFE 和播放 low-water 监控。

## 后续建议项目

1. 摄像头、IMU、磁力计、触觉、电池和充电状态测试。
2. PSRAM/内部 SRAM 分配压力、BundleFS 掉电恢复、屏幕休眠/唤醒和应用生命周期压力测试。
3. Wi-Fi 扫描、RSSI、DHCP/DNS/NTP、网关发现、断网重连与漫游测试；需要新增受控 Host 诊断契约。
4. 语音 AFE 空环、编码耗时、上传队列、播放 low-water/overflow 的结构化快照；需要扩展 VoiceDiagnostics。
5. 轮足底盘通信、急停、心跳、命令超时、状态回传及 Bear 动画/语音/运动联动测试；应在底盘协议确定后加入独立模块。

## 构建

```sh
python3 tools/micropixel package guest/apps/system-diagnostics --aot-target riscv32-ilp32f
```

输出位于 `build/apps/system-diagnostics/`。构建成功不代表真机项目已经通过，所有硬件项仍需在目标设备执行。
